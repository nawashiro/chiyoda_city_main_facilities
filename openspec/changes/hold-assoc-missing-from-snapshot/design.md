# Design

## Context

`./fac assoc --osm-id` はOSM APIから要素の実データを取得し、`data/osm-decisions.json`へ`method: human`の判断を保存したうえで、`apply_decisions`で`data/places.jsonld`へ参照と座標を適用します。要素の収録有無は確認しません。

保持スナップショットは`imports/openstreetmap/raw.json`（gitignore対象）と、そのSHA256と版を持つ`imports/openstreetmap/retrieval.json`（追跡対象）の組です。`src/osm_maintenance.py`の`verified_snapshot`が両者の一致を検証しており、月次更新はこの検証を通った取得物だけを使います。取得物は名称のない要素を落として保存されます。

月次更新の関連付け判定は型付きIDの収録有無で既存参照を継続します。収録がなければ候補・QID・Jevで再評価し、確定できなければ確認Issueへ戻します。保留は`status: hold`、`previous`、`reason`、`human`を持ち、判定・提示・カテゴリ再評価の対象外になります。解除は`assoc --osm-id`か`assoc --choice none`による人の確定だけです。

CLIは保守者の端末で実行され、`imports/openstreetmap/raw.json`はgitignore対象のため、fresh clone直後や取得を行っていない作業ツリーには存在しません。

## Goals / Non-Goals

**Goals:**

- 次の月次更新が無効化する関連付けを、確定判断として記録しない
- スナップショットを取得していない作業ツリーでも`assoc`を使えるままにする
- 記録・解除を既存の保留の仕組みに載せ、新しい状態を増やさない

**Non-Goals:**

- 月次更新側の判定変更（人の判断ではなく取得物側で保留へ倒す案は採らない）
- 保持スナップショットの自動取得や自動解除
- 公開ミラー`site/mirrors/osm.json`による照合（関連付け済み要素だけを含むため収録の有無を判定できない）

## Decisions

### 収録の有無は保持スナップショットで判定し、時刻比較は使わない

判定材料は`verified_snapshot`が返す取得物の要素IDの集合です。要素の最終編集時刻と取得版を比べる案は採りません。既存参照の継続はIDの収録で決まるため、取得より後に編集されていてもIDが収録されていれば月次更新は再審査しません。時刻比較は不要な保留を増やします。

`verified_snapshot`を通すのは、作業ツリーの`raw.json`が追跡対象の取得メタと別の取得物である場合に、別スナップショットで判定しないためです。

### 未収録の要素は、その要素を`previous`に持つ保留として記録する

人の意図は「その要素へ付け替える」ことなので、`previous`に指定要素を残します。`places.jsonld`へは参照を付けず、座標も変更しません。カテゴリ判断は既存の保留と同じく取り消します。

確定判断として保存する案は、次の月次更新が要素を見つけられず再審査へ戻し、その後の「該当なし」でリンクが失われるため採りません。エラーで拒否する案は実地調査で得た要素IDを保持できず、次の取得まで同じ作業をやり直すことになるため採りません。自動で`--choice none`にする案は、人が選んでいない「該当なし」を判断記録へ書くため採りません。

### 照合できない場合は警告して従来どおり記録する

`imports/openstreetmap/raw.json`が無い、または`verified_snapshot`が失敗する場合は、照合しなかったことを`WARNING`で示し、指定要素を確定した判断として記録します。CLIが保守者の端末で動く以上、取得物の無い状態を通常の状態として扱う必要があります。保留へ倒す案はfresh cloneでの`assoc`をすべて保留にしてしまうため採りません。

`WARNING`には照合しなかった理由と、保留になった場合の解除手順（ミラー更新後の`assoc --osm-id`再実行）を含めます。

### 保留は自動解除しない

既存仕様どおり、解除は人の確定だけに限ります。要素が次の取得物に収録されても、月次更新は保留を維持します。自動解除を許すと、実地調査待ちの保留と取得待ちの保留が同じ状態に混ざり、どちらが解除されてよいかをコードが区別できなくなります。

## Risks / Trade-offs

- [スナップショットが無い作業ツリーでは守れない] → `WARNING`で照合しなかったことを示し、`docs/reference/cli.md`に照合条件を書く
- [古い取得物で不要な保留になる] → 保留は理由と取得版つきで残り、ミラー更新後に`assoc --osm-id`を再実行すれば確定判断に置き換わる
- [自動保留でカテゴリ判断が消える] → 既存の保留と同じ挙動として受け入れ、理由に取得版を残して再判断の手掛かりにする
- [保留中は公開recordに参照が付かない] → `previous`に要素IDを残し、解除手順を`WARNING`とdocsに示す

## Migration Plan

1. `assoc --osm-id`の照合と保留への分岐、テスト、docsを変更する
2. 既存データの移行はない。スナップショットの無い作業ツリーでは従来どおり動作する
3. ロールバックは変更を含むコミットを戻すだけ。判断記録の形式は変わらない
