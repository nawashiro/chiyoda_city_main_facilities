# Design

## Context

更新の起点は`update-osm.yml`で、取得・照合後に確認用または反映用のPRを作る。`resolve_osm_candidates.py`は同じ接続設定のモデルを三役で呼び、`github_osm_review.py`はYAMLの回答を取得物全体へ適用する。取得物はActions artifactにも保存するため、長期間残る確認には保存期間の問題がある。

`data/places.jsonld`が公開データの正本である。検索対象は出典別の入力に分かれ、WAM由来の対象も含む。削除対象のコードと、維持する施設・座標・帰属表示を区別して移行する。変更の目的と範囲は`proposal.md`に記す。

## Goals / Non-Goals

**Goals:**

- 取得から公開までを一つの更新経路にし、確定分の自動反映と施設単位の人手判断を両立する。
- 人の判断を、次回取得とIssue回答の両方で検証できる形で保存する。
- 既存施設の識別子と公開契約を維持して、WAMと古い確認経路を削除する。

**Non-Goals:**

- JSON-LD以外の公開形式、確認用Webアプリ、施設の自動追加、Releaseの自動作成は扱わない。

## Decisions

### 1. 検索入力と判断の保存先をそれぞれ一つにする

検索入力を`inputs/facilities.json`へ統合する。人が編集する項目は施設UUID、名称、検索座標、任意のQID、公開除外指定とする。現在の出典別ファイルから対象を移し、重複UUIDや検索に必要な情報の欠落は検証エラーにする。公開正本から取得用の設定を逆生成する方法は、検索の意図が公開データに混ざるため採用しない。

`data/osm-decisions.json`に施設ごとの最新の判断根拠、判定方法、選択結果、Jevの信頼度・確率・使用量、人の確定、確認Issue番号、反映待ち状態を保存する。根拠には施設情報と候補の事実を保存し、SHAだけを残す方法は採用しない。判断記録を公開JSON-LDやPagesの配布物へ含めない。

取得物と取得元・ハッシュは`imports/openstreetmap/`に残す。生成できる候補一覧や一時レポートは正本にせず、確認の継続をActions artifactの保存期間に依存させない。

### 2. 人の確定を優先し、既存参照・QID・Jevで照合する

同じ根拠に対する人の確定があれば最初に適用する。「該当なし」を既存参照やQID一致で上書きしない。その後は`osm-maintenance`の順序と条件で照合する。OSM IDは常に`node/123`など型を含む値で扱う。

名称と50m以内の座標は候補の抽出に使い、自動確定には使わない。既存参照の継続は、前回の型付きIDが今回の取得物にあることを中心に、既存の名称・50m・QID矛盾の検査を維持する。過去の名称・近接座標だけの判定結果は移行時に再評価する。過去の誤一致を既存参照として固定しないためである。

根拠のハッシュは、施設の名称・検索座標・QIDと、判定へ渡す候補の型付きID・名称・座標・QID・識別用タグから生成する。候補をID順に正規化し、取得日時や配列順の変化ではハッシュが変わらないようにする。Jevへ渡す識別用タグは許可リストで固定し、保存する根拠と一致させる。プロンプトやモデルを変更しても、同じ事実に対する人の判断は維持する。

### 3. Jevの選択と信頼度で人手確認の要否を決める

TypeSafe System Oneの`POST /v1/systemone`を直接呼ぶ。初期設定は`jev-1.14.0`、認証はActions secretの`TYPESAFE_API_KEY`とする。Chat Completions互換層や別モデルへの切り替えは設けない。[System One API](https://docs.typesafe.ai/api/system-one)、[モデル一覧](https://docs.typesafe.ai/models)に基づく。

決定的な照合で残った施設ごとに、一回の`choice`で候補と「該当なし」を選ばせる。選択肢を候補IDに対応させ、実際の日本語名称と保存した根拠を渡す。応答の選択肢、信頼度、確率の範囲と選択肢集合を検証する。自由文の説明を生成させず、Issueの理由は判定経路・信頼度・競合・参照消失などの事実から組み立てる。[Choice API](https://docs.typesafe.ai/primitives/choice)にある選択肢数の上限を超える入力や、モデルの入力上限を超える入力は、黙って削らず実行エラーにする。

初期の自動確定条件は`confidence >= 0.90`とする。これは正答率90%を意味しない。信頼度は選択肢の確率分布に基づくため、既知の誤一致、同名施設、同一建物内の別施設、「該当なし」を含む固定事例で判定を検証する。[信頼度の定義](https://docs.typesafe.ai/confidence)に従い、閾値は実測に基づいて調整する。既存参照の解除や複数施設間の候補競合は、高信頼度でも人へ回す。

2026-10-27時点の公開料金は入力100万トークン当たり0.042米ドル、出力は無料である。1施設5,000入力トークンと仮定すると、18施設で約0.0038米ドル、96施設でも約0.0202米ドルになる。これは呼び出し数と入力長を仮定した試算であり、実費は応答の使用量から記録する。名称と近接座標による自動確定を残す費用上の理由は乏しいため、残件はJevへ渡す。[料金](https://docs.typesafe.ai/models)

### 4. 施設ごとのIssueで候補選択と確定を受け付ける

同じ施設の未解決Issueを再利用する。本文には施設名、現在の参照、候補の名称・型付きID・距離・地図とOSMへのリンク、確認理由、Jevの選択と信頼度を示す。Jevを呼んでいないケースは、その理由を示す。

各候補と「該当なし」の通常のMarkdownチェックボックスに、独立した「この選択を確定する」を加える。選択が一つで確定欄もチェックされた場合だけ回答として扱う。途中の編集やコメントは反映しない。通常のチェックボックスを採用し、廃止されたtasklistブロックは使わない。[GitHubのtask list仕様](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/about-tasklists)

Issue内の機械可読部分には施設UUIDと根拠ハッシュを置くが、Issue本文を正本として信用しない。候補集合・根拠・現在の判断記録と照合し、回答編集者のリポジトリwrite権限以上をAPIで確認する。候補IDの改変、複数選択、古い根拠の回答は適用せず、修正理由をコメントする。GitHub上の発言は`[bot]`で始める。

取得し直して根拠が変わった場合は候補と確定欄を更新し、古い選択を解除する。根拠が同じ場合は途中の選択を保ち、再通知しない。確定した判断は最新の正本へ施設単位で適用し、取得時点のデータ全体で上書きしない。正本の検証とPages公開が成功してからIssueを閉じる。

### 5. 月次更新とIssue回答を同じworkflowで処理する

`update-osm.yml`に月次`17 3 1 * *`（毎月1日03:17 UTC、日本時間12:17）、`workflow_dispatch`、`issues: edited`を設定する。日時は本提案の初期値である。月次・手動実行は取得から行い、Issue編集は保存済み根拠への回答反映だけを行う。Issueイベント用のworkflowはデフォルトブランチに配置する。[ActionsのIssueイベント](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#issues)

更新から公開までの同時実行を直列化し、実行中の処理を取り消さない。待機実行が置き換わっても回答を失わないよう、各実行で判断記録にある未解決Issueの確定済み回答を読み直す。その場合も確定編集者の権限を確認する。人の新しい確定と月次判定の適用前に、最新の正本・根拠・候補の施設間重複を再検証する。

必要な権限はデータ反映用の`contents: write`、確認用の`issues: write`、既存Pages公開用の権限とする。自動コミットで通常のpush起点workflowが起動することに依存せず、`publish-pages.yml`を`workflow_call`で明示的に呼び、反映コミットSHAを渡す。[GITHUB_TOKENによるイベントの制約](https://docs.github.com/en/actions/how-tos/writing-workflows/choosing-when-your-workflow-runs/triggering-a-workflow)

Pages側は渡されたSHAの正本を検証して公開する。公開前にmainとの関係を確認し、古い実行が新しいデータを上書き公開しないようにする。公開失敗時はActionsを失敗とし、Issueを開いたまま再実行できる状態を残す。既に反映した判断の再実行は新しい変更を生まないようにする。

二段階PRは更新と人手判断の双方を止めるため削除する。単独の施設判断を変更するために、取得物全体への承認を求めない。

### 6. WAMと重複経路を削除する

WAM専用の取得・更新・契約コード、検索入力、保存ファイル、設定、テスト、workflowを削除する。公開JSON-LDからWAM識別子を除き、施設UUID・対象集合・利用可能な座標を維持する。WAM由来の施設を検索入力へ移してから元入力を削除する。残る座標等に必要な出典・帰属表示は文書へ移す。

`reidentify-sources.yml`と重複する再同定処理、YAML確認workflow、古いPRを閉じる処理、三者投票の設定・実装・テストを削除する。取得物のハッシュ検証など必要な処理だけを通常更新へ移す。現行の未対応CLI引数も統一した起動経路で解消する。

WAMは参照先・利用条件・残るデータの帰属表示を文書に残す。公開JSON-LDの契約、OSM/Wikidataの帰属表示、手動Release公開は維持する。旧経路を互換目的で並行稼働させない。

## Risks / Trade-offs

- 日本語名称でのJev誤判定 → 既知の失敗事例を評価に含め、閾値だけで正しさを保証しない。判断根拠と実際の使用量を保存する。
- 既存の誤一致が継続する → 名称・近接座標だけで確定した既存結果を移行時に再評価する。
- Issue編集と月次取得の競合 → 根拠ハッシュ、確定編集者、最新正本を反映直前に検証する。古い回答は適用しない。
- 自動コミットがブランチ保護で拒否される → 実装時にmainの実際の保護設定を確認する。必要な設定変更を明示し、検証や保護を黙って回避しない。
- GitHubの定期実行の遅延・停止 → 月内の実行を前提とし、時刻の厳密性を求めない。手動再実行とActionsの失敗通知を残す。
- 未確定の間は古い公開参照が残る → Issueに前回参照と判断待ちを明記し、確定後に置換または解除する。未確定を不採用として記録しない。

## Migration Plan

1. 現行の施設UUID・検索対象・座標・関連参照を記録する。WAM由来の対象を統合入力へ移し、公開除外指定も契約どおり扱う。
2. 照合、Jev接続、判断記録、Issue回答、明示的な参照解除を実装し、取得済みデータと固定API応答で検証する。古いYAMLの未完了判断を無条件で移植せず、現在の根拠から必要なIssueを作る。
3. `TYPESAFE_API_KEY`とActionsの必要権限を設定する。既知の誤一致を含む少数の実データでJevの選択・信頼度・費用を測り、自動確定条件を確認する。検証結果と設定値を記録する。
4. WAMと旧経路を削除し、運用文書と既存仕様のPurposeを新しい契約に合わせる。差分仕様を反映した後、テスト・入力検証・公開データ検証・Pagesビルドを通す。
5. mainに反映し、手動実行で取得、確定分の自動反映、Pages公開、Issueでの確認と解除を確認する。その後は月次実行へ任せる。

公開データに問題が出た場合は、該当するデータ変更をGitで戻してPagesを再公開する。外部APIや自動処理の問題はworkflowを停止して修正する。削除した旧経路をフォールバックとして復活させない。
