# Design

## Context

公開正本は`data/places.jsonld`、検索入力は`inputs/facilities.json`、判断記録は`data/osm-decisions.json`である。OSMの取得物とハッシュは`imports/openstreetmap/`へ保存する。既存接続の継続と、失われた接続の再接続を分け、入力全体の変化を成立済み接続の再審査に使わない。

## Goals / Non-Goals

- 既存の接続を維持し、接続がない対象だけを一意なQID・Jevで照合する。
- 確定分を公開し、不確かな候補だけを人に確認する。
- 判断をGitへ保存してから提示し、回答はその保存済み候補へ反映する。
- 施設の実在判定、OSM編集、検索入力の自動削除、汎用的な再開機構は扱わない。

## Decisions

### 1. 取得条件を維持し、既存IDの接続を優先する

名前のない要素の除外を含む現在のOSM取得条件を維持する。型付きOSM IDが取得結果にあれば、名称・座標・タグ・QIDが変化しても接続を維持する。距離やQIDの再検査、過去の照合方法を理由にした再審査は行わない。

既存IDがなければ一意なQID一致を適用する。それでも決まらず候補がある場合にJevを使う。新しい検索対象にも同じ照合経路を使い、以前の接続の有無で通知を分けない。名称と50m以内の距離は候補抽出に使い、自動確定の理由にはしない。

### 2. Jevと人の判断を必要な範囲で再利用する

JevはTypeSafe System Oneの`choice`、モデル`jev-1.14.0`、`TYPESAFE_API_KEY`を使う。候補IDまたは`none`を選ばせ、`confidence >= 0.90`なら自動反映する。失われた既存参照の置換・解除も対象とする。低信頼度と施設間の重複割り当ては確認Issueへ回す。通信・認証・応答検証の失敗は実行エラーとする。

人が選んだOSM IDを正本に保存し、以後は既存参照として維持する。人の`none`は同じ照合根拠では維持し、根拠が変われば再判定する。未解決のJev結果も根拠が同じなら再利用する。

根拠ハッシュは対象の名称・座標・QIDと候補の型付きID・名称・座標・QID・識別用タグから生成する。候補順と取得日時は影響させない。ハッシュは未解決の照合の再利用と提示更新に用い、成立済み接続の失効条件にはしない。

### 3. 接続先なしは一つの通知にまとめる

候補がなければJevを呼ばず、既存のOSM参照と照合由来のWikidata参照を解除する。Jevの高信頼度の`none`と人の`none`も同じ参照解除を行う。UUIDと有効な座標は残し、施設や検索入力を自動削除しない。

接続先がない検索対象を一つの通常Issueへ列挙する。検索入力の除去またはOSMへの収録の判断は人に委ねる。この通知には確定欄を設けない。同じ内容で閉じられた通知は再提示せず、対象が変わったときに更新する。

### 4. 判断の保存とIssue提示を分ける

月次・手動更新は、回答の読み込み、取得、判定、正本と判断記録への反映、検証、コミット・push、Issue提示、該当SHAの公開の順とする。`present`は保存済み判断だけを読み、取得・Jev呼び出し・判断記録の書き換えを行わない。pushが失敗した場合は提示せず停止する。取得からのリトライループやIssue本文からの判断復元は追加しない。

確認Issueは施設IDのマーカーで検索して再利用する。番号は人の回答を保存するときに記録する。同じ根拠のIssueは途中の選択を保ち、手動で閉じられていても開き直さない。根拠が変わった場合は本文と選択欄を更新する。

### 5. 回答処理を保存済み候補への反映に限定する

回答処理は未解決Issueの現在の本文を読み、施設ID、保存済み候補または`none`の一つの選択、確定欄、編集者のwrite権限、重複割り当てを確認する。説明文・信頼度・本文全体・入力ハッシュの一致は必須にしない。イベントに添付された古い本文ではなく現在のIssueを読む。

有効な回答を最新正本へ施設単位で反映し、Git保存、Pages公開、Issueクローズへ進む。取得・Jev判定・未解決Issueの再提示は行わない。公開失敗時は確認Issueを閉じず、保存済みコミットの公開を再実行できる。

### 6. 更新・公開の既存経路を使う

`update-osm.yml`は月次`17 3 1 * *`、手動起動、Issue本文編集を受け付ける。更新と回答を`osm-maintenance`で直列化し、実行中の処理を取り消さない。公開workflowへ反映SHAを渡し、公開成功後だけ回答済みIssueを閉じる。

WAM専用処理、三者投票、YAML確認、二段階PRを除去し、統合入力・単一Jev・Issue回答へ統一する。公開形式、UUID、帰属表示を維持し、判断記録を配布物へ含めない。

## Risks / Trade-offs

- 存在するIDへの誤った既存接続は自動では直らない。接続の修正は人が行う。
- Jevの信頼度は正答率ではない。固定応答による閾値・不正応答・既知の混同の回帰テストを行う。
- Git保存後のIssue提示が失敗すると、通知が遅れる。保存済み判断で`present`を再実行できる。
- 外部からmainが更新されpushが競合した場合は停止する。再計算を自動で繰り返さず、原因を確認して再実行する。

## Migration Plan

1. 仕様と運用文書を最終方針へ揃える。
2. 既存接続の継続、参照解除、一括通知、保存後の提示、回答処理を変更する。
3. 回帰テスト、入力・正本検証、Pagesビルド、OpenSpec検証を通す。
4. mainへコミット・pushする。実データの再取得や人の回答は通常の運用経路で行う。
